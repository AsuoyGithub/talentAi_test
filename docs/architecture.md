# Architecture

## Overview

TalentAI is a layered Python application. It separates domain data, parsing,
matching, persistence, and delivery so each part can be changed independently.

```text
CLI / HTTP API
      |
      v
Services (resume parser, matching engine)
      |
      v
SQLite repository
      |
      v
Domain models
```

## Modules

| Module | Responsibility |
| --- | --- |
| `domain.py` | Candidate, Job, and MatchResult value objects |
| `config.py` | Environment-backed runtime settings |
| `services/parser.py` | Plain-text resume extraction and validation |
| `services/matcher.py` | Deterministic scoring and ranking |
| `services/report.py` | CSV and JSON match report generation |
| `storage.py` | SQLite schema, transactions, and persistence |
| `api/server.py` | HTTP routing and JSON serialization |
| `cli.py` | Developer and operator command line |
| `seed.py` | Reproducible demo data |

## Domain Model

```text
Candidate 1 -------- * MatchResult * -------- 1 Job
```

- `Candidate` is the input supplied by a recruiter or parsed from a resume.
- `Job` defines the requirements used by the matching engine.
- `MatchResult` is an immutable snapshot produced for one candidate and job.

Skill labels are normalized to lowercase, whitespace-collapsed, sorted tuples
before they are used by services or persisted.

## Request Flow

1. The API validates the HTTP method and path.
2. The repository loads or stores a domain object.
3. The resume parser extracts fields when a resume is submitted.
4. The matching engine compares a job with candidates.
5. The API writes `MatchResult` rows and returns JSON.

## Persistence

The repository uses SQLite and enables foreign keys for every connection.
Schema creation is idempotent and owned by `SqliteRepository`.

Entity IDs are generated by `new_id()` as short string identifiers such as
`candidate_1a2b3c4d5e6f`. JSON arrays store normalized skill and reason
values.

The HTTP server uses `ThreadingHTTPServer`, so the repository opens its SQLite
connection with `check_same_thread=False`. SQLite serializes writes, and the
single database file keeps local deployment simple.

## Configuration

Settings are read from environment variables and have safe local defaults.
Database path, host, port, and upload size can be overridden without changing
application code.

## Design Decisions

- **No external runtime dependencies:** the application remains easy to run,
  package, and audit.
- **Deterministic matching:** scoring is transparent and reproducible.
- **Small modules:** each module has one clear responsibility and can be tested
  in isolation.
- **Standard-library HTTP server:** adequate for this local, low-traffic API
  while keeping the deployment surface small.
- **String entity IDs:** they avoid exposing database auto-increment values and
  keep demo fixtures stable across fresh installations.
